# [Step 4] std::thread 기반 멀티스레드 에코 서버 구현

## 1. 개요 (Overview)
* **목표:** 단일 클라이언트만 처리할 수 있었던 기존 동기식 서버의 한계를 극복하고, C++11의 `std::thread`와 모던 C++의 이동 언어(Move Semantics)를 활용해 다중 접속을 동시 처리하는 **Thread-per-Client 아키텍처 서버**를 구축한다[cite: 1].
* **학습 키워드:** `std::thread`, `join()` vs `detach()`, RAII 소유권 이동(`std::move`)[cite: 1], C++14 초기화 캡처(Init Capture)[cite: 1], `std::mutex`, `std::lock_guard`, 경합 상태(Data Race), Thread-per-Client, C10K 문제

## 2. 핵심 아키텍처 및 동작 원리

### ① 메인 스레드와 워커 스레드의 역할 분리
* **메인 스레드 (Acceptor Thread):** `while(true)` 루프 안에서 무한히 `Accept()`를 호출하며 접속 요청만 대기한다[cite: 1]. 클라이언트가 접속하면 소켓 제어권을 확보한 뒤, 워커 스레드를 생성·분리(`detach()`)하고 즉시 다음 접속 수신으로 돌아간다[cite: 1].
* **워커 스레드 (Worker Thread):** 메인 스레드로부터 `std::move`를 통해 소켓 소유권을 넘겨받은 독립 실행 흐름이다[cite: 1]. 담당 클라이언트가 접속을 끊을 때까지 전용 에코 루프(`Recv`/`Send`)를 수행하며, 통신이 종료되면 스스로 소멸한다[cite: 1].

### ② 자원 분리와 `detach()` 실행 흐름
```text
[Main Thread]  ── Accept() ──> [Client Connected] ──> [Create Worker Thread]
      │                                                     │ (std::move)[cite: 1]
      │ <────── [detach() / Return to Accept()] ───────────┤
      ▼                                                     ▼
 [Next Accept]                                       [Worker Thread Loop]
                                                      └── Recv() -> Send()[cite: 1]
                                                      └── Socket Close on exit[cite: 1]
```

## 3. 깊이 있는 개념 정리 (Deep Dive)

### ① `std::thread` 자원 회수 방식 비교
스레드 객체가 소멸할 때 `joinable() == true` 상태이면 C++ 런타임은 `std::terminate()`를 호출하여 프로세스를 강제 종료시킨다. 따라서 반드시 소멸 전 자원 정리 방식을 선택해야 한다.

| 구분 | `join()` | `detach()` |
| :--- | :--- | :--- |
| **동작 방식** | 메인 스레드가 대상 스레드 종료까지 대기 | 대상 스레드를 객체와 분리하여 백그라운드 독자 실행 |
| **블로킹 여부** | **Yes** (메인 스레드가 멈춤) | **No** (생성 즉시 다음 코드로 진행) |
| **적용 목적** | 단일 스레드와 동일해져 동시 처리 불가 | **동시 접속 처리를 위한 필수 선택** |

### ② 복사 불가 소켓의 이동 연산과 C++14 초기화 캡처
* **복사 금지 이유:** `TcpSocket`은 Double Close 방지를 위해 복사 생성자가 삭제되어 있다 (`= delete`)[cite: 1].
* **람다 클로저 메커니즘:** C++14의 초기화 캡처 구문(`[client = std::move(client)]`)을 사용하면 컴파일러가 생성하는 람다 익명 클래스의 멤버 변수로 `TcpSocket` 이동 생성자가 호출된다[cite: 1].
* **자원 자동 해제:** 람다 함수가 종료되면 람다가 소유한 `TcpSocket` 멤버 변수의 소멸자가 불리면서 `close()`가 자동 수행된다 (RAII 기법)[cite: 1].

### ③ 콘솔 출력(`std::cout`) 경합 상태와 RAII 동기화
* **Data Race:** 여러 워커 스레드가 전역 스트림인 `std::cout`에 동시에 접근하면 출력 결과가 서순 없이 난잡하게 섞인다.
* **RAII Lock:** 전역 `std::mutex log_mtx;`를 선언하고, 출력 구문마다 `std::lock_guard<std::mutex> lock(log_mtx);`를 적용하여 안전한 상호 배제(Mutual Exclusion)를 보장한다.

### ④ Thread-per-Client 모델의 물리적 한계 (C10K 문제)
* **스택 메모리 폭증:** 스레드 1개당 기본 스택 메모리(약 8MB)가 할당되므로, 접속자 1,000명 동시 유지 시 순수 스택으로만 8GB 메모리가 소모된다.
* **컨텍스트 스위칭 오버헤드:** CPU 코어 수보다 스레드가 지나치게 많아지면 연산 처리 시간보다 스레드를 교체하는 컨텍스트 스위칭 비용이 커진다.

## 4. 트러블슈팅 노트 (Troubleshooting)

### ① 이동 전용(Move-only) 객체의 C++14 초기화 캡처 시점 및 소유권 이관
* **문제 현상:** `[client = std::move(client)]` 구문 작성 시 캡처 대상 객체 불일치 및 컴파일 에러 발생.
* **원인 분석:** `TcpSocket`은 Double Close 방지를 위해 복사 생성자가 삭제된 RAII 객체이므로 이동 연산(`std::move`)으로만 소유권 이전이 가능하다. 메인 스레드 스택에 소켓 객체가 완전히 생성되기 전에 람다 클로저를 정의하려 하면 유효한 소유권 이전 경로가 파괴된다.
* **해결 방법:** 메인 스레드에서 `Accept()` 시스템 콜을 완결시켜 유효한 소켓 객체를 스택에 확정지은 뒤, C++14 초기화 캡처(Init Capture)를 통해 람다의 멤버 변수로 이동 생성자(`Move Constructor`)를 호출하도록 구조를 재설계한다.

### ② 스레드 간 버퍼 공유로 인한 데이터 레이스(Data Race) 및 메모리 오염
* **문제 현상:** `main()` 스택 영역에 선언된 `buf`에 워커 스레드가 접근을 시도할 때 컴파일 에러 및 데이터 오염 현상 발생.
* **원인 분석:** 프로세스 단위의 공유 메모리 공간을 다수의 스레드가 동시 읽기/쓰기를 수행하면 락(Lock) 없이 데이터 오염(Data Race)이 발생한다.
* **해결 방법:** 입출력 버퍼 선언부를 람다 함수 내부(각 워커 스레드의 독립된 스택 메모리 영역)로 격리시켜, 별도의 동기화 오버헤드 없이 스레드 안전성(Thread-safety)을 확보한다.

### ③ 네트워크 I/O 연산 포함으로 인한 임계 영역(Critical Section) 과도 확충
* **문제 현상:** 동기화 뮤텍스(`log_mtx`) 잠금 범위 안에 소켓 송신 연산(`client.Send()`)을 포함시켜 스레드 간 병목 현상 및 성능 저하 발생.
* **원인 분석:** 네트워크 I/O 연산은 소켓 상태 및 네트워크 RTT(Round Trip Time)에 지연되는 블로킹 작업이다. 이를 임계 영역 내부에 남겨두면 데이터 송신이 완료될 때까지 다른 모든 워커 스레드의 콘솔 출력 및 로깅 작업이 연쇄적으로 대기(Lock Contention)하게 된다.
* **해결 방법:** `std::lock_guard` 스코프 중괄호(`{}`)를 활용해 잠금 범위를 최소 단위인 `std::cout` 출력 로직으로만 엄격히 제한하고, 네트워크 송신 작업은 Lock 해제 후 독립 실행되도록 분리한다.
