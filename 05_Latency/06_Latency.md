# [Step 4] Thread-per-Client 모델의 Latency 측정 개선 및 멀티스레드 병목 검증

## 1. 개요 (Overview)
* **목표:** 멀티스레드 기반(Thread-per-Client) 소켓 통신 환경에서 동시 접속자가 늘어날 때 발생하는 실제 지연(Latency) 현상을 정확히 측정하고 검증한다.
* **학습 및 개선점:** 초기에는 서버 측에서 Latency를 측정하려 했으나 구조적 결함을 발견하고, 클라이언트 주도의 RTT(Round Trip Time) 측정 방식으로 아키텍처를 전면 수정하여 신뢰할 수 있는 성능 지표를 도출해냈다.

---

## 2. 문제 인식: 서버 측 Latency 측정의 치명적 함정

초기 테스트 코드는 서버의 워커 스레드 내부에서 `client.Send()` 함수 앞뒤로 시각을 재어 Latency를 측정했다. 하지만 동시 접속자를 늘려도 지연 시간이 비현실적으로 짧게 나오는 문제가 있었다.

### ❌ 기존 방식의 문제점
* **`Send()` 함수의 실체:** C/C++ 소켓의 `Send()`는 클라이언트에게 패킷이 도달했을 때 리턴하는 것이 아니라, **내 OS 커널의 송신 버퍼(`SO_SNDBUF`)에 데이터를 복사하는 순간 즉시 리턴**한다. 
* **진짜 병목의 누락:** 내가 정말 측정하고 싶었던 것은 수백 개의 스레드가 띄워졌을 때 발생하는 **'컨텍스트 스위칭(Context Switching)으로 인한 스레드 대기 시간'**이었다. 클라이언트가 데이터를 보냈음에도 서버 스레드가 제때 깨어나지 못해 `Recv()`가 지연되는 현상은 `Send()` 앞뒤를 재는 방식으로는 절대 포착할 수 없었다.

### ✅ 해결 방향: 클라이언트 주도 RTT 측정
서버는 비즈니스 로직 없이 받은 패킷을 그대로 반환하는 **순수 Echo 서버**로 역할을 축소했다. 대신, 클라이언트 스레드가 `Send`를 호출한 직후부터 `Recv`로 응답을 돌려받기까지의 **왕복 지연 시간(RTT, End-to-End Latency)**을 측정하도록 구조를 뒤집었다. 이를 통해 네트워크 이동 시간과 서버의 스레드 경합 지연을 모두 포함한 '진짜 Latency'를 확인할 수 있었다.

## 3. 트러블슈팅 및 벤치마크 고도화 과정 (Troubleshooting)

이 과정에서 겪은 자잘한 이슈들과 이를 해결하며 알게 된 멀티스레딩 성능 측정의 노하우를 정리했다.

###  측정 데이터를 오염시키는 `std::cout` 락(Lock) 병목
* **상황:** 클라이언트가 RTT를 측정할 때마다 루프 안에서 `std::cout`으로 지연 시간을 출력하도록 작성했다.
* **문제:** 100개 이상의 스레드를 띄우자 Latency가 비정상적으로 치솟았다. 원인은 서버의 소켓 처리 지연이 아니라, **`std::cout` 내부의 동기화 락(Mutex) 때문**이었다. 수많은 스레드가 콘솔에 로그를 찍기 위해 줄을 서면서 대기 시간이 RTT 측정치에 포함되어 버린 것이다.
* **해결:** 루프 안에서는 `std::cout`을 완전히 제거했다. 대신 스레드별 로컬 변수(`local_total_ms`, `local_max_ms`)에 락 없이 통계를 집계한 뒤, 스레드가 종료되는 시점에 딱 한 번만 전역 뮤텍스(`std::mutex`)를 잡고 메인 통계에 합산하도록 수정하여 병목을 없앴다.


###  클라이언트 무한 루프와 종료 조건(`runtime`)의 필요성
* **상황:** "클라이언트 루프에서 굳이 시간(runtime)을 체크하며 빠져나와야 하나?"라는 의문이 들었다.
* **문제:** 종료 조건이 없으면 스레드가 영원히 데이터를 주고받는다. 메인 스레드에서 `t.join()`이 블로킹된 상태로 멈춰버리므로, 앞서 공들여 만든 **'최종 통합 통계'를 영원히 화면에 출력할 수 없게 된다.**
* **해결:** 통제된 벤치마크를 위해 `duration_cast`를 활용한 테스트 시간(runtime) 제한 로직을 확립했다. 시간이 지나면 루프를 `break`하여 스레드를 정상 종료시키고, 취합된 통계를 확인할 수 있도록 구성했다. (지정된 횟수만큼 통신하고 종료하는 Count 방식도 대안이 될 수 있음을 깨달았다.)

###  Echo 서버 오버헤드 최소화 및 연결 안정성 확보
* **상황:** 클라이언트 구조를 고치면서 서버 코드도 함께 점검했다.
* **문제 및 해결:** 
  1. **불필요한 연산 제거:** 루프마다 1KB 버퍼를 0으로 초기화하는 `memset`은 부하 테스트에 불필요한 CPU 자원을 먹으므로 삭제했다.
  2. **순수 Echo 구현:** `buf[len] = '\n'` 처럼 버퍼를 변형해놓고 전송 길이는 `len`으로 고정하여 데이터가 깨지는 버그를 잡고, 받은 크기 그대로 반환하도록 순수하게 수정했다.
  3. **Backlog 확장:** 수백 개의 스레드가 동시에 `Connect`를 때리면 OS 큐가 감당하지 못하므로, 서버의 `Listen` 백로그를 `100000` 으로 넉넉하게 늘려 연결 거절(Connection Refused)을 방지했다.

## 4. 결론 및 Next Step

이러한 시행착오 끝에 **"멀티스레드 환경의 벤치마크는 측정 툴(Client) 자체의 병목(Lock, I/O)부터 완벽히 통제해야 한다"**는 중요한 교훈을 얻었다. 

정교해진 측정 클라이언트를 통해 동시 접속자를 점진적으로 늘려본 결과, 특정 임계점(스레드 수 > CPU 코어 수 수십 배)을 넘어가면 서버의 RTT가 걷잡을 수 없이 튀는(Spike) 현상을 내 눈으로 직접 수치로 확인할 수 있었다.

### 🚀 Next Step: Non-blocking I/O & `epoll`
스레드를 무한정 늘리는 Thread-per-Client 구조는 한계(Context Switch 비용, 메모리 고갈)가 명확하다. 다음 단계에서는 서버를 논블로킹(Non-blocking) 모드로 전환하고, 단일 스레드 혹은 소수의 스레드로 수천 개의 소켓 이벤트를 처리하는 **Linux `epoll` 기반 아키텍처**로 고도화하여 C10K 문제를 돌파해 볼 것이다.
